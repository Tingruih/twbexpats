# 打者「非典型打席/投球情境」排除需求

> 本文件只整理需求與已達成的共識，**不包含解法/架構設計**（例如函式命名、程式碼結構、實作步驟），留待下一階段的設計文件處理。

## 背景

`site_builder/stats/tables/vs_pitch_types.py` 產出打者對戰各球種（及球種分組）的統計表，欄位包含 strike_pct、zone_pct、o_swing_pct、whiff_pct、avg、woba、barrel_pct 等。這些統計假設每一球都來自「正常投手 vs 正常打席意圖」的對戰，但實際比賽中存在兩種會汙染這個假設的情境：

1. **野手代投（position player pitching）**：比分懸殊時球隊派野手上場投球，球質、控球都跟真正投手差非常多，打者面對這種投手打出的高 wOBA/AVG 不具代表性。
2. **短打嘗試（bunt attempt）**：打者擺出觸擊姿勢時，揮棒/揮空的判斷邏輯跟正常打擊決策完全不同，不應該被算進「打者面對這個球種時，正常評估後選擇揮棒或放過」的統計裡。

目前這兩種情境都**沒有**被排除，會混在現有的 vs_pitch_types 統計裡。

## 需求範圍（已確認）

排除邏輯只適用於以下入口：

- `compute_vs_pitch_types`
- `compute_vs_pitch_groups`
- `compute_pitch_group_usage_by_count`（`usage_by_count.py`）
- `compute_batter_pitch_hand_splits`（因為它是包著上面三個函式做 all/L/R 手別切分，會自動連帶受影響）

**明確不動**：

- `season_stats` 來源的官方產季統計（AVG/OBP/ERA 等，來自 MLB 官方數字，不適合自行改寫定義）
- `compute_batter_statcast` 組裝出的整體 Statcast 摘要（whiff%、chase% 等總計指標）

## 排除項目一：野手代投

- **定義**：該球的對戰投手，其真實守備位置不是投手、也不是二刀流（例如 Ohtani 這種本來就會投球的兩刀流球員不算），視為野手代投，這球應該被排除。
- **資料現況**：目前完全沒有存投手守備位置的相關欄位。
- **技術上已確認可行**：投手的真實守位資訊（`primaryPosition`），已經包含在 `extract.py` 目前抓取比賽資料時使用的同一份 API 回應（`{BASE_URL}/game/{game_pk}/withMetrics`）裡，不需要額外呼叫新的 API 端點或建立新的資料庫快取表。已用真實案例（曾野手代投的球員 Willians Astudillo）驗證：他代投那場比賽的「boxscore 角色」顯示投手，但同一份回應裡的 `primaryPosition` 正確顯示他真實的守位（三壘手）。

## 排除項目二：短打嘗試

- **定義**：打者做出短打動作相關的投球結果（揮空短打、界外觸擊、觸擊界外碰觸等），不應該算作一般的揮棒/揮空判斷。
- **資料現況**：目前逐球資料裡已經有欄位可以判斷是否為短打嘗試（球的判定結果代碼、以及打進場內時的飛行軌跡分類），不需要新抓資料。
- **已知限制**：如果打者只是「擺出短打姿勢但沒有揮棒，被投出好球或壞球」（take bunt，中途縮桿），目前資料沒有專屬欄位可以辨識這種情況，**無法排除**——只能排除「有實際揮棒/觸擊動作」的短打嘗試。這個限制先明確記錄下來，不在本次需求範圍內解決。

## 已達成共識的決策

1. 排除邏輯的適用範圍僅限上述三張表（見「需求範圍」），不影響官方統計或整體 Statcast 摘要。
2. 不新增 API 呼叫、不新增資料庫快取表——野手守位資訊直接沿用抓取層現有已讀取的資料來源。
3. **不回填歷史資料**：這個排除邏輯只對「之後新抓的比賽」生效；已經快取在資料庫裡的舊 `pitches_json` 缺少必要欄位時，預設視為「不知道、不排除」，不做任何額外的回填處理或標記。
4. 排除邏輯需要設計成**可擴充的框架**，方便未來如果發現其他「非典型打席/投球情境」時，可以用同樣的方式加入，而不需要每次都重新設計呼叫方式。

## 尚待確認 / 開放問題

- 未來若要新增其他排除類別，是否每次都需要重新評估「資料是否已存在於現有抓取內容裡」，還是可以假設都比照這兩個案例處理。
- 短打嘗試若剛好是該打席的最後一球（例如短打飛球被接殺、短打滾地出局），排除這球是否等同於整個打席的結果都不算進該球種桶的 PA outcome 統計——這是設計階段需要明確定義的行為，本文件只記錄現況與待決事項，不預先下結論。
